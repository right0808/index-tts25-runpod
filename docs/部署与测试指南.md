# IndexTTS 2.5 RunPod Load Balancing 部署与测试指南

本文档说明如何从 GitHub 仓库部署 IndexTTS 2.5 到 RunPod Serverless Load Balancing Endpoint，以及如何使用仓库内的 Python 脚本完成从零 Worker 冷启动、参考音频上传、语音合成、结果下载和 WAV 校验。

## 1. 部署结构

当前部署使用以下组件：

- GitHub 仓库：`right0808/index-tts25-runpod`
- 部署分支：`load-balancer`
- Dockerfile：`/Dockerfile`
- 模型：`IndexTeam/IndexTTS-2.5`，Worker 启动时从 Hugging Face 下载
- 推理后端：vLLM `0.27.0` 和固定版本的 vLLM-Omni
- Endpoint 类型：RunPod Serverless **Load Balancer**
- 对外 API：FastAPI `POST /tts`
- 输出文件：22.05 kHz 单声道 WAV，上传到配置的 OSS 服务

Load Balancing Endpoint 将 HTTP 请求直接转发给 Worker，不使用 Queue Endpoint 的 `/run`、`/runsync` 和 `runpod.serverless.start()` 协议。因此必须选择 **Load Balancer** 类型，不能选择 Queue 类型。

项目主要文件：

| 文件 | 用途 |
| --- | --- |
| `Dockerfile` | 构建 vLLM、vLLM-Omni 和应用镜像 |
| `start-lb.sh` | 启动模型服务、业务网关、FastAPI 和健康服务 |
| `lb_app.py` | 实现 `/ping`、`/ready` 和 `/tts` |
| `lb_fallback.py` | 模型冷启动期间提供健康响应并代理长时间合成请求 |
| `deploy/indextts2_5_serverless.yaml` | IndexTTS 2.5 两阶段推理配置 |
| `worker/` | 参数校验、参考音频处理、vLLM 调用和 OSS 上传 |
| `scripts/test_load_balancer_api.py` | 完整线上 API 测试脚本 |

## 2. 部署前准备

需要准备：

1. 可用的 RunPod 账号和 API Key。
2. RunPod 已连接 GitHub，并且能够读取 `right0808/index-tts25-runpod`。
3. 一个兼容本项目协议的 OSS 服务：
   - 上传：`POST /oss`
   - 上传文件字段：`file`
   - 鉴权请求头：`X-API-Key`
   - 成功状态码：HTTP 201
   - 响应至少包含 `fileName`
   - 文件读取地址：`GET /oss/{fileName}`
4. 建议先使用 48 GB GPU，例如 NVIDIA A40 或 RTX A6000。24 GB GPU 尚未作为稳定配置完成验证。
5. 至少 64 GB Container Disk。

请勿把 RunPod Key、OSS API Key、私钥或本地 `.env` 提交到 GitHub。

## 3. 在 RunPod 创建 Secret

进入 RunPod 控制台的 Secret 管理页面，创建：

```text
Name: OSS_UPLOAD_API_KEY
Value: 真实的 OSS 上传 API Key
```

Endpoint 环境变量中通过下面的引用使用它：

```text
{{ RUNPOD_SECRET_OSS_UPLOAD_API_KEY }}
```

不要直接把真实 OSS Key 写入 Endpoint 的普通环境变量。

## 4. 创建 Load Balancing Endpoint

在 RunPod Serverless 页面创建 Endpoint：

1. 选择从 GitHub 仓库导入。
2. 选择仓库 `right0808/index-tts25-runpod`。
3. Branch 填写 `load-balancer`。
4. Dockerfile Path 填写 `/Dockerfile`。
5. Build Context 填写 `.`。
6. Endpoint Type 必须选择 **Load Balancer**。
7. GPU 先选择 A40 48 GB 和 RTX A6000 48 GB。
8. GPU Count 设置为 `1`。
9. Container Disk 设置为 `64 GB` 或更高。
10. Minimum CUDA Version 设置为 `12.0` 或更高。
11. Execution Timeout 设置为 `1800` 秒。
12. 开启 FlashBoot。

### 4.1 Worker 和缩容配置

推荐配置：

```text
Minimum Workers: 0
Maximum Workers: 1
Idle Timeout: 300 seconds
Scaler Type: Request Count
Scaler Value: 3
```

`Minimum Workers=0` 表示没有常驻 Worker，空闲时不会持续占用 GPU。第一次请求会触发 GPU 分配、容器启动、模型下载和模型加载，可能需要数分钟。

不要把 Idle Timeout 设置成 5 秒之类的极小值。IndexTTS 模型尚未完成冷启动时，RunPod 可能因为短时间没有业务请求而回收 Worker，形成反复启动。`300` 秒允许冷启动和一次合成完成，空闲 5 分钟后仍会自动缩容到零。

当前每个 Worker 内部串行执行推理。`Maximum Workers=1` 时，如果同一时间提交第二个合成请求，可能收到 HTTP 429 `WORKER_BUSY`。Load Balancing Endpoint 没有请求队列，客户端应根据 `Retry-After` 重试。

### 4.2 端口配置

RunPod Template 必须同时声明：

```text
8000/http,8001/http
```

环境变量必须设置：

```text
PORT=8000
PORT_HEALTH=8001
HEALTH_CHECK_PATH=/ping
```

- `8000`：用户访问的业务 API 端口。
- `8001`：RunPod 独立健康检查端口。
- 两个端口不能设置成相同值。
- `/ping` 在模型加载期间也返回 HTTP 200，防止长时间冷启动被判定为容器故障。
- `/ready` 只有在模型真正可推理时才返回 HTTP 200。

## 5. Endpoint 环境变量

在 RunPod Endpoint 中配置：

```text
OSS_BASE_URL=http://your-oss.example.com
OSS_UPLOAD_API_KEY={{ RUNPOD_SECRET_OSS_UPLOAD_API_KEY }}
OSS_EXPIRES_SECONDS=3600
OSS_HTTP_TIMEOUT=30

MODEL_ID=IndexTeam/IndexTTS-2.5
VLLM_STARTUP_TIMEOUT=1800
VLLM_REQUEST_TIMEOUT=1800

PORT=8000
PORT_HEALTH=8001
HEALTH_CHECK_PATH=/ping
```

可选限制参数：

```text
MAX_TEXT_CHARS=3000
MAX_REFERENCE_AUDIO_BYTES=26214400
MAX_OUTPUT_AUDIO_BYTES=104857600
LB_UPSTREAM_TIMEOUT=1900
```

说明：

| 变量 | 说明 |
| --- | --- |
| `OSS_BASE_URL` | OSS 服务公开基础地址，程序会自动去除末尾的 `/` |
| `OSS_UPLOAD_API_KEY` | OSS 上传密钥，只通过 RunPod Secret 提供 |
| `OSS_EXPIRES_SECONDS` | 生成音频在 OSS 中的有效时间 |
| `OSS_HTTP_TIMEOUT` | OSS 上传及下载超时秒数 |
| `MODEL_ID` | Hugging Face 模型 ID |
| `VLLM_STARTUP_TIMEOUT` | 模型启动最长等待时间 |
| `VLLM_REQUEST_TIMEOUT` | 单次 vLLM 合成最长等待时间 |
| `MAX_TEXT_CHARS` | 最大输入字符数 |
| `MAX_REFERENCE_AUDIO_BYTES` | 单个参考音频最大字节数 |
| `MAX_OUTPUT_AUDIO_BYTES` | 生成 WAV 最大字节数 |
| `LB_UPSTREAM_TIMEOUT` | 负载均衡轻量网关等待内部 FastAPI 的超时秒数 |

## 6. 构建和发布

保存 Endpoint 后，RunPod 会从 `load-balancer` 分支构建 Docker 镜像。构建过程需要从 GitHub 安装固定版本的 vLLM-Omni，因此需要允许构建环境访问 GitHub。

构建完成后检查：

1. Endpoint 的镜像标签对应最新 Git commit。
2. Worker 使用的 Endpoint Version 是最新版本。
3. Template Ports 为 `8000/http,8001/http`。
4. `workersMin=0`、`workersMax=1`。
5. 没有请求时，Workers 页面中没有 `RUNNING` Worker；历史 `EXITED` 记录不代表 Worker 仍在计费运行。

模型启动日志中应依次看到类似阶段：

```text
stage=model_server_start
stage=load_balancer_gateway_start
stage=load_balancer_app_start
stage=health_server_start
```

模型文件由 Hugging Face 下载。未配置持久化模型缓存时，新机器冷启动可能重新下载模型。

## 7. API 协议

Endpoint 基础地址：

```text
https://ENDPOINT_ID.api.runpod.ai
```

所有请求使用 RunPod Key：

```text
Authorization: Bearer RUNPOD_API_KEY
```

### 7.1 健康检查

```http
GET /ping
```

模型已经就绪时的响应：

```json
{
  "status": "healthy",
  "model_status": "ready"
}
```

### 7.2 就绪检查

```http
GET /ready
```

状态说明：

| HTTP 状态 | 响应状态 | 含义 |
| --- | --- | --- |
| 200 | `ready` | 模型可以接受合成请求 |
| 503 | `starting` | Worker 已启动，但模型仍在加载 |
| 503 | `failed` | vLLM 启动失败，响应中包含诊断信息 |

### 7.3 语音合成

```http
POST /tts
Content-Type: application/json
```

请求示例：

```json
{
  "text": "大概两到三天就可以送到哈。",
  "language": "zh",
  "speaker_audio": "https://example.com/speaker.m4a",
  "emotion_audio": "https://example.com/emotion.m4a",
  "emotion_alpha": 0.8,
  "speed": 1.0,
  "text_normalization": true
}
```

参数说明：

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `text` | 是 | 合成文本，默认最多 3000 字符 |
| `speaker_audio` | 是 | 公开 HTTP(S) 音频 URL 或 audio data URL |
| `language` | 否 | `zh`、`en`、`zhen`、`ja`、`es`、`ar` 或 `yue`，默认 `zh` |
| `emotion_audio` | 否 | 情绪参考音频 URL |
| `emotion_vector` | 否 | 8 个情绪数值，顺序为 happy、angry、sad、afraid、disgusted、melancholic、surprised、calm |
| `emotion_text` | 否 | 自然语言情绪描述 |
| `emotion_alpha` | 否 | 情绪强度，范围 `0.0` 到 `1.0` |
| `speed` | 否 | 语速，范围 `0.5` 到 `2.0` |
| `text_normalization` | 否 | 是否进行文本规范化，默认 `true` |

`emotion_audio`、`emotion_vector` 和 `emotion_text` 最多只能使用一种。

成功响应：

```json
{
  "audio_url": "http://oss.example.com/oss/generated.wav",
  "file_name": "generated.wav",
  "content_type": "audio/wav",
  "bytes": 449068,
  "sample_rate": 22050,
  "channels": 1,
  "duration_seconds": 10.182,
  "expires_in_seconds": 3600,
  "elapsed_ms": 9373
}
```

常见错误：

| HTTP 状态 | 错误 | 处理方式 |
| --- | --- | --- |
| 422 | `INVALID_INPUT` | 修正请求参数或音频 URL |
| 429 | `WORKER_BUSY` | 根据 `Retry-After` 延迟重试 |
| 502 | `INFERENCE_FAILED` | 查看 Worker 日志和 vLLM 错误 |
| 502 | `UPSTREAM_FAILED` | 检查 OSS、网络及依赖服务 |
| 503 | `MODEL_STARTING` | 等待冷启动并重试 `/ready` |
| 503 | `MODEL_FAILED` | 查看响应中的 vLLM 启动诊断 |

## 8. 使用 Python 脚本测试

### 8.1 本地准备

安装 Python 依赖：

```bash
python -m pip install requests
```

在仓库外层创建 `.env`，不要提交：

```text
RunPodKey=你的RunPod_API_Key
OSS_BASE_URL=http://your-oss.example.com
OSS_UPLOAD_API_KEY=你的OSS上传Key
OSS_EXPIRES_SECONDS=3600
OSS_HTTP_TIMEOUT=30
```

准备：

- 音色音频：`fxd.m4a`
- 情绪音频：`emotion1.m4a`
- 测试脚本：`scripts/test_load_balancer_api.py`

### 8.2 完整测试命令

在仓库目录执行：

```bash
python scripts/test_load_balancer_api.py \
  --endpoint-id ENDPOINT_ID \
  --env-file ../.env \
  --speaker ../fxd.m4a \
  --emotion ../emotion1.m4a \
  --output ../index-tts25-test-output.wav \
  --text '大概两到三天就可以送到哈，收到以后您可以品鉴一下哦如果觉得好喝也可以找我，您保留好我的微信有任何问题就随时找我哦'
```

当前部署的 Endpoint ID 为 `44s1tva2fqnvku`，因此当前环境可以执行：

```bash
python scripts/test_load_balancer_api.py \
  --endpoint-id 44s1tva2fqnvku \
  --env-file ../.env \
  --speaker ../fxd.m4a \
  --emotion ../emotion1.m4a \
  --output ../index-tts25-test-output.wav \
  --text '大概两到三天就可以送到哈，收到以后您可以品鉴一下哦如果觉得好喝也可以找我，您保留好我的微信有任何问题就随时找我哦'
```

脚本会自动完成：

1. 从 `.env` 读取配置，但不打印真实 Key。
2. 持续请求 `/ready`，触发并等待 scale-to-zero Worker 冷启动。
3. 把音色音频和情绪音频上传到 OSS。
4. 调用 `POST /tts`。
5. 打印请求过程、HTTP 状态和 JSON 结果。
6. 下载生成的 WAV。
7. 校验文件头是否为 RIFF/WAVE。
8. 保存到 `--output` 指定路径。

日志示例：

```text
stage=configuration ... api_key="[REDACTED_SECRET]"
stage=cold_start ...
stage=readiness ... http_status=503 response={"status":"starting"}
stage=readiness ... http_status=200 response={"status":"ready"}
stage=oss_upload ... http_status=201
stage=tts_request POST /tts started ...
stage=tts_response ... http_status=200
stage=audio_download ... riff_wave=true
stage=complete API test passed ...
```

可调整参数：

```text
--cold-start-timeout 1800
--request-timeout 1800
--health-request-timeout 45
--poll-interval 15
--language zh
--emotion-alpha 0.8
--speed 1.0
```

第一次 `/ready` 超时或返回 `no workers available` 不一定表示部署失败。scale-to-zero 的 GPU 分配和容器启动期间可能暂时没有可路由 Worker，测试脚本会继续重试。

### 8.3 代码单元测试

```bash
python -m pytest -q
```

当前预期结果：

```text
19 passed
```

## 9. 使用 curl 手工检查

检查模型是否就绪：

```bash
curl -H "Authorization: Bearer ${RUNPOD_API_KEY}" \
  https://ENDPOINT_ID.api.runpod.ai/ready
```

参考音频必须先位于 Worker 可访问的公开 URL。然后调用：

```bash
curl -X POST \
  -H "Authorization: Bearer ${RUNPOD_API_KEY}" \
  -H 'Content-Type: application/json' \
  https://ENDPOINT_ID.api.runpod.ai/tts \
  -d '{
    "text": "这是一次语音合成测试。",
    "language": "zh",
    "speaker_audio": "https://example.com/speaker.m4a",
    "emotion_audio": "https://example.com/emotion.m4a",
    "emotion_alpha": 0.8,
    "speed": 1.0
  }'
```

## 10. 常见故障排查

### 10.1 `no workers available` 或连接超时

这是 scale-to-zero 冷启动阶段的常见现象。确认：

- `workersMax` 大于 0。
- GPU 类型有可用资源。
- 客户端持续重试 `/ready`。
- 冷启动超时至少为 1800 秒。
- Idle Timeout 不要短于模型启动时间。

### 10.2 `/ping` 无法访问

确认：

- Template Ports 为 `8000/http,8001/http`。
- `PORT=8000`。
- `PORT_HEALTH=8001`。
- `HEALTH_CHECK_PATH=/ping`。
- `PORT` 与 `PORT_HEALTH` 不相同。

### 10.3 `/ready` 长时间返回 `starting`

在 RunPod Workers 页面打开当前 Worker 日志，检查：

- Hugging Face 模型是否仍在下载。
- Container Disk 是否不足。
- GPU 是否 CUDA OOM。
- vLLM 是否成功监听 `127.0.0.1:8092`。

如果 `/ready` 返回 `failed`，响应中会附带 `/tmp/vllm-server.failed` 保存的最后一段启动日志。

### 10.4 构建阶段安装 vLLM-Omni 失败

确认构建环境可以访问 GitHub，并检查 Dockerfile 中的固定提交是否仍可获取。本项目使用 vLLM `0.27.0`，不要单独把基础镜像降级到 `0.26.0`，否则可能发生 vLLM 与 vLLM-Omni API 不匹配。

### 10.5 HTTP 429 `WORKER_BUSY`

单 Worker 一次只执行一个合成请求。等待 `Retry-After` 指定秒数后重试，或者在确认显存和成本后提高 `workersMax`。Load Balancing Endpoint 不会替客户端排队。

### 10.6 合成成功但无法下载音频

确认：

- `OSS_BASE_URL` 能从公网访问。
- OSS 返回的 `fileName` 可以通过 `/oss/{fileName}` 下载。
- OSS 有效期没有过短。
- OSS 服务允许 RunPod Worker 上传。

## 11. 更新部署

代码修改完成后推送到：

```bash
git push origin load-balancer
```

等待 RunPod 构建新镜像。生产更新时确认旧 Worker 已退出、新 Worker 使用最新 Endpoint Version 和镜像标签，再运行完整 Python 测试。

只修改客户端测试脚本或文档不会改变容器运行逻辑，但 GitHub 自动构建仍可能生成一个新镜像。
